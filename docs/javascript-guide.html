Perf Framework: JavaScript Files Explained

This guide explains how the Node.js files work together to run a JMeter test. The basic flow is: 

Terminal command → index.js → run-id.js / jmx.js → docker.js → JMeter container
Source note: The exact contents of jmx.js and run-id.js were not provided here. Their sections explain their reported roles and known function signature. Check those files to confirm details such as how XML is edited and how IDs are formatted.

1. cli/index.js: coordinates a test run

This is the command-line entry point. It reads the user’s options, prepares the run directory and test file, then calls the Docker runner.

Imports

  • Command from commander defines and reads terminal commands and options.
  • generateRunId imports the function that creates a unique identifier for a run.
  • prepareJMX as prepareJmx imports a function from jmx.js and uses the local name prepareJmx. The as keyword renames the imported function in this file.
  • path provides helpers for building file paths.
  • runJMeterInDocker imports the function that starts JMeter through Docker.
  • mkdir creates the results directory. It is asynchronous, so the code uses await.

Registering the command

const program = new Command();

Creates a Commander program. The code then registers a command named run, which is why the terminal command includes node cli/index.js run. 

.requiredOption('--script <path.jmx>', 'Path to the JMX script')
.requiredOption('--name <testName>', 'Name of the test')

These options are mandatory. A test needs a JMX file and a name. 

.option('--threads <number>', 'Number of threads', '10')
.option('--duration <seconds>', 'Duration of the test', '60')
.option('--rampup <seconds>', 'Ramp-up time', '10')

These options are optional. If omitted, Commander uses the provided defaults. Commander normally gives option values to the program as strings, such as "10", even when the value represents a number.

The action function

.action(async (options) => { ... })

Commander calls this function after it recognizes the run command. The options object contains the values entered by the user and any defaults.

  1. generateRunId() creates an identifier to distinguish this test run from other runs.
  2. const { script, name, threads, duration, rampup } = options; uses JavaScript destructuring to copy those properties into separate variables.
  3. path.resolve('results', runId) creates an absolute path for this run’s results folder.
  4. await mkdir(resultsDir, { recursive: true }) creates that folder. recursive: true also creates missing parent folders.
  5. path.resolve(script) converts the supplied script path to an absolute path based on the current working directory.
  6. prepareJmx(...) prepares a working JMX file in the run’s results folder. It should work on a copy so the original test plan stays unchanged.
  7. runJMeterInDocker(...) receives the prepared JMX path, InfluxDB URL, test name, run ID, and load settings.
  8. The catch block handles errors thrown by those operations. console.error prints the problem and process.exit(1) marks the command as failed.

Reading the command line

program.parse(process.argv);

process.argv contains the words typed in the terminal. Commander reads those words, matches them to the registered options, and starts the action function.

2. cli/run-id.js: names a run

This module exports generateRunId(). The CLI calls it once at the beginning of a run. The ID is used to keep each run’s output separate and to identify its metrics.

The precise format depends on the implementation in your file. In general, a run ID often combines the current time with a short random value to make collisions unlikely. The function should return a string.

3. cli/jmx.js: prepares the test plan

The function reported in your file is: 

prepareJMX(originalJMXPath, runId, testName, resultsDir)

Its job is to prepare the JMX file for one run. Based on the function signature and intended workflow, it receives:

  • originalJMXPath: where the user's original JMX lives.
  • runId: this run’s unique ID.
  • testName: the name used to identify the test.
  • resultsDir: where the run’s working copy and output belong.

The intended result is a working JMX copy, possibly with runtime settings or an InfluxDB Backend Listener prepared for the run. The function’s return value should be the path to that prepared JMX file, because index.js passes it to docker.js.

Important: JMeter JMX files have a strict XML structure. Test elements such as samplers, timers, and controllers must be paired with their corresponding <hashTree> elements. If the preparation code parses and rebuilds XML, it must preserve that order and nesting. A malformed prepared copy can make JMeter fail even when the original file looks correct.

4. cli/docker.js: starts JMeter in Docker

The shared implementation exports this function: 

runJMeterInDocker(
  runId, jmxPath, influxdbUrl, testName, threads, duration, rampup
)

Imports and function setup

  • spawn from node:child_process starts an external program—in this case, the Docker CLI.
  • path helps find the directory and filename of the prepared JMX file.
  • path.dirname(jmxPath) gets the folder containing the JMX.
  • path.basename(jmxPath) gets just the JMX filename.

Building the Docker command

The args array contains the Docker command and its arguments. Using an array with spawn keeps each argument separate.

ArgumentPurpose
run Starts a new Docker container.
--rm Deletes the container after it exits. Files in the mounted results folder remain.
--network=infra_jmeter-network Connects the container to the Docker network where InfluxDB is reachable.
-v resultsDir:/results Makes the run folder available inside the container at /results.
perf-framework-jmeter:5.6.3 Selects the JMeter image to run.
-n Runs JMeter in non-GUI mode.
-t Tells JMeter which test plan to execute.
-l and -j Set the JTL results file and JMeter log file.
-Jname=value Passes a property into JMeter, such as thread count or run ID.

Starting Docker and handling its result

spawn('docker', args, { stdio: 'inherit' })

Starts Docker with the arguments in the array. stdio: 'inherit' sends Docker and JMeter output directly to the terminal. 

child.on('error', reject);

If Node.js cannot start the Docker process at all—for example, if Docker is missing—this rejects the returned Promise. 

child.on('close', (code) => { ... });

Runs when the Docker process exits. A code of 0 usually means success. A nonzero code indicates failure.

Current behavior to be aware of: the shared docker.js resolves the Promise for both success and failure. On failure it resolves with a nonzero code rather than rejecting. If index.js does not check that returned code, it can print “Test run completed” even when JMeter failed. The exit code should be checked and propagated so a failed run is reported accurately.

Putting the pieces together

  1. You enter node cli/index.js run ... in the terminal.
  2. Commander reads the options in index.js.
  3. run-id.js creates a unique ID.
  4. index.js creates a results folder.
  5. jmx.js prepares a working test plan.
  6. docker.js starts a JMeter container with that test plan.
  7. JMeter saves its log and JTL file into the mounted results folder.

Useful JavaScript concepts used here

  • Import: makes code from another file or package available.
  • Export: lets another file import a function.
  • Function arguments: values passed into a function.
  • Destructuring: pulls named values out of an object.
  • Promise: represents work that finishes later.
  • async / await: make asynchronous code easier to read.
  • Event: a notification such as a child process closing.
  • Exit code: a number used by a command to report success or failure.
