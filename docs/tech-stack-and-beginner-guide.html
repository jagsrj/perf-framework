You do not need to master every technology before reading the code. Start with the run flow, then follow one step at a time from the browser to the server and database.

01 · PRODUCT OVERVIEW

What the application does

  1. Define a scenarioGive the test a name and configure virtual users, duration, and ramp-up.
  2. Upload a JMeter planSelect a `.jmx` file; the app validates its XML and records a version and hash.
  3. Run JMeter locallyThe Node.js app starts JMeter in a Docker container on the same machine.
  4. Monitor the testJMeter streams live metrics to InfluxDB, which Grafana visualizes.
  5. Review the resultsThe app summarizes the JTL output and compares it with a matching earlier run.

Where each kind of data is stored

JMX scripts and JTL/log artifactsLocal filesystemFiles are not stored in PostgreSQL.
Live time-series measurementsInfluxDBUsed for timestamped metrics and dashboard queries.
Charts and dashboardsGrafanaVisualizes InfluxDB metrics.

Architecture at a glance

              └── InfluxDB (Docker network)
                    └── Grafana dashboard (localhost:3000)

Host application

Node.js and Express serve the UI/API and coordinate database, filesystem, and Docker work.

Docker services

Compose runs PostgreSQL, InfluxDB, and Grafana; JMeter runs in a per-test container.

Local-only boundary

One active web-managed run at a time. Remote worker scheduling and distributed execution are not implemented.

Docker Desktop supplies the container runtime on macOS. The app itself runs directly on the host; Docker containers use the laptop's CPU, memory, and disk.

03 · TECHNOLOGIES

Technology stack

JavaScript and Node.js

JavaScript is the language used by the CLI, server, and browser UI. Node.js runs JavaScript outside the browser. The project uses ES modules:

import path from 'node:path';
import express from 'express';

export function helper() {
  // ...
}
  • import loads another module; export makes code available to other modules.
  • async/await handles operations that complete later, such as SQL queries and file reads.
  • node:fs/promises accesses files; node:child_process starts programs such as Docker.
  • "type": "module" in package.json enables ES module syntax. The project requires Node.js 18 or newer.

npm

npm installs packages and runs named project commands. package.json lists dependencies and scripts; package-lock.json records resolved versions; node_modules/ is generated and should not be committed.

npm install       # Install dependencies
npm run web       # Start the web application
npm test          # Run automated tests

Express and HTTP APIs

Express maps HTTP requests to route handlers. HTTP uses a method (what to do) and a path (which resource):

RoutePurpose
GET /api/scenariosList scenarios.
POST /api/scenariosCreate a scenario.
POST /api/scenarios/:id/scriptUpload a JMX script.
POST /api/scenarios/:id/runsStart a run.
GET /api/runs/:runId/resultsGet report and baseline data.

Express middleware performs shared work before routes, such as parsing JSON and serving static files. See web/server.js.

HTML, CSS, and browser JavaScript

HTML

web/public/index.html describes forms, navigation, and page sections.

CSS

web/public/styles.css controls layout, colors, responsive behavior, and status badges.

Browser JavaScript

web/public/app.js handles clicks, submits forms, calls APIs with fetch, and updates the page.

The browser's DOM (Document Object Model) is its live representation of the HTML. Regular API calls send JSON; file uploads use FormData.

PostgreSQL and SQL

PostgreSQL is a relational database: tables contain rows and columns. Primary keys identify records; foreign keys link records.

scenarios 1 ── many scenario_script_versions
scenarios 1 ── many test_runs
  • scenarios: scenario name, load settings, and current script metadata.
  • scenario_script_versions: one record per uploaded script revision, with path and SHA-256.
  • test_runs: execution configuration snapshot, state, timestamps, and JSONB summary.

The pg package connects Node.js to PostgreSQL. Use parameterized queries for values instead of building SQL strings from user input:

await pool.query(
  'SELECT * FROM scenarios WHERE id = $1',
  [scenarioId]
);

$1 is a placeholder. The separate parameter value helps keep user input from changing the SQL command. JSONB stores the structured run summary as queryable JSON.

Apache JMeter

Apache JMeter is the load-testing engine. A .jmx file is an XML test plan. JMeter runs non-GUI inside the custom image built from jmeter/Dockerfile.

The framework provides runtime properties such as virtual users, duration, ramp-up, InfluxDB URL, application name, and run ID. The run ID associates emitted metrics with a specific execution. cli/jmx.js prepares the plan and adds the InfluxDB Backend Listener/run tag when needed.

Docker and Docker Compose

Docker runs processes in containers with isolated filesystems and networking. Docker Compose describes a group of related services.

  • Compose starts PostgreSQL, InfluxDB, and Grafana.
  • The app starts a JMeter container for a run.
  • Named volumes retain database/Grafana data when containers are recreated.
  • A bridge network lets containers reach each other by service name.
  • Bind mounts expose the prepared JMX and output folder to JMeter.

See infra/docker-compose.yml and cli/docker.js. docker compose down retains named volumes by default; adding -v deletes those volumes and their data.

InfluxDB and Grafana

InfluxDB stores time-series measurements: values associated with timestamps and filterable tags. JMeter's Backend Listener writes metrics to the jmeter database; this project configures one-day retention.

Grafana queries InfluxDB as a data source and displays charts. The dashboard filters on scenario/application and run ID. PostgreSQL summaries support durable history/comparison; InfluxDB supports live time-based charts.

05 · FOLLOW A TEST

How a web run works

Browser UIUser starts scenario
Express APIValidates & records run
Docker / JMeterExecutes prepared plan
InfluxDBReceives live metrics
GrafanaCharts by run ID
  1. The browser sends POST /api/scenarios/:id/runs.
  2. Express loads the scenario and checks that a script has been uploaded.
  3. The server creates a run ID and results/<run-id>/; it snapshots the source JMX.
  4. PostgreSQL records the script hash/version and the exact run settings.
  5. cli/jmx.js prepares a JMX copy with the metrics listener/run tag.
  6. cli/docker.js starts a detached JMeter container and mounts the script read-only and the results directory for output.
  7. JMeter writes the JTL/log files and streams live measurements to InfluxDB.
  8. The server waits for JMeter to exit, summarizes the JTL, and stores the aggregate summary in PostgreSQL.
  9. The UI polls run status; Grafana uses the run ID to filter charts.

Run states

Starting→ Running→ CompletedFailedAborted

The database constraint currently allows one active run. On server restart, Docker labels help the app find and resume monitoring its active JMeter container.

06 · UNDERSTAND THE REPORT

Summaries and baseline comparison

JTL is a CSV file containing individual sample outcomes such as elapsed time, label, and success. web/summary.js reads it as a stream, so the app does not need to load the entire file into memory.

As each row arrives, the summary code updates overall and per-label aggregates and records response times in HDR histograms. The final summary includes:

Volume & errors

Total samples, failed samples, and error rate.

Latency

Mean, p95, p99, and maximum response time.

Transactions

Separate totals and latency summaries for each JMeter label.

The Test Results page compares against the latest earlier completed run matching the same scenario, script hash, virtual users, duration, and ramp-up. That exact match helps make comparisons meaningful. If there is no matching baseline, the report says so.

07 · GET HANDS-ON

Run the application locally

Install Docker Desktop/Engine, Docker Compose, Node.js 18+, and npm. From the project root:

# Start PostgreSQL, InfluxDB, and Grafana
docker compose -f infra/docker-compose.yml up -d

# Build the JMeter image (first time, or after Dockerfile changes)
docker build -t perf-framework-jmeter:5.6.3 ./jmeter

# Install JavaScript dependencies
npm install

# Start the web application
npm run web

Open http://localhost:4000. Create a scenario, upload a trusted `.jmx` plan, start a test, then visit Runtime Monitoring and Test Results.

Run automated tests

npm test

Run with the CLI

node cli/index.js run \
  --script scripts/sample.jmx \
  --name smoke-test \
  --threads 10 \
  --duration 60 \
  --rampup 10

The CLI and web app both invoke JMeter in Docker. Start Compose first if you want live InfluxDB metrics.

08 · BUILD WITH CONFIDENCE

Tests and development workflow

The project uses Node's built-in node:test runner and node:assert/strict; no additional test framework is needed.

Test fileCoverage
test/docker.test.jsDocker argument construction and stop behavior.
test/jmx.test.jsJMX preparation and run-ID tagging.
test/summary.test.jsJTL aggregates and stream error handling.
test/results.test.jsBaseline metric comparisons.

When adding a feature

  1. Identify which UI, API, persistence, and external-service layers are affected.
  2. Validate input and use existing database patterns.
  3. Use parameterized SQL and surface errors clearly.
  4. Add a focused test for the new behavior.
  5. Run npm test and node --check path/to/changed-file.js.
  6. Update the guide or README if setup or user behavior changed.

Example: a read-only API endpoint

app.get('/api/example', asyncHandler(async (request, response) => {
  const result = await pool.query(
    'SELECT run_id, status FROM test_runs ORDER BY started_at DESC LIMIT 20'
  );
  response.json(result.rows);
}));

In the browser, use the existing api() helper:

const recentRuns = await api('/api/example');

For user-provided values, validate them and use SQL placeholders. Never turn arbitrary user input into a filesystem path.

09 · OPERATE RESPONSIBLY

Safety and operations notes

  • JMX plans are executable test plans. Use only scripts and targets you trust and are authorized to test.
  • The web app is for local development, binds to loopback, and does not have user authentication.
  • Compose has development-only credentials and enables anonymous read-only Grafana access for the local dashboard. Do not expose these defaults as a shared service.
  • Scripts and run artifacts are files outside PostgreSQL; back them up separately if needed.
  • Docker volumes contain PostgreSQL, InfluxDB, and Grafana data. Removing volumes deletes their data.
  • The current product is single-host and permits one active web-managed run. It has no remote worker registry, queue, distributed scheduler, or high availability.
Important: docker compose down -v deletes the named volumes and the data in them. Use docker compose down to stop/remove containers while retaining named-volume data.
